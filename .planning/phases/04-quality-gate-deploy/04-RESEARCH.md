## Summary

The stack is already in place and the app architecture is simpler than the roadmap text suggests: the preview is a `srcdoc` iframe (`sandbox="allow-scripts"`, no `allow-same-origin`) that loads React 18 UMD, Babel standalone and Tailwind v4 browser build **from jsdelivr CDN inside the iframe**. Sandpack is NOT used at runtime (only `hasDefaultExport` from `sandpack-files.ts` is imported). The README must describe the srcdoc architecture, not Sandpack.

For e2e, the installed `ai@7.0.141` exposes `MockLanguageModelV4` and `simulateReadableStream` from `ai/test` (and `simulateReadableStream` from `ai`). `@ai-sdk/google@4` models are `specificationVersion = "v4"`, so V4 is the correct mock. The route consumes `result.fullStream`; the mock stream must emit `text-start`, `text-delta` (field `delta`), `text-end`, `finish`. A mid-stream failure is a stream that emits some deltas then an `{type:"error"}` part (or errors the ReadableStream); the route already converts both into a body error (`controller.error`) after status 200, which the client shows as the friendly alert + retry.

Three non-obvious traps dominate planning: (1) the route returns 500 when `GOOGLE_GENERATIVE_AI_API_KEY` is missing - in CI/e2e there is no key, so the key check must be bypassed in mock mode; (2) the new 5/min/IP rate limit will break the e2e suite (>5 generations from one IP in a minute) unless limits are raised via env in the Playwright `webServer.env`; (3) `model.ts` currently evaluates `google(MODEL_ID)` at import time - mock selection must be a request-time function (read `process.env` inside it), and `route.test.ts` mocks `@/lib/ai/model` as `{ model: {} }` so the test mock shape must be updated together.

**Primary recommendation:** Add `getModel()` (and `isE2EMock()`) to `src/lib/ai/model.ts`, add `src/lib/rate-limit.ts` (pure, injectable clock), wire both in `route.ts`; install `@playwright/test` + `@vitest/coverage-v8`; keep Vitest and Playwright separated by directory (`e2e/` excluded from Vitest); one `ci.yml` with two jobs; deploy via Vercel Git integration behind `checkpoint` tasks.

### Pattern 1: Mock model (verified against installed `ai@7.0.141`)
`MockLanguageModelV4({ doStream })` where `doStream` returns `{ stream: ReadableStream<LanguageModelV4StreamPart> }`. Stream parts (from `@ai-sdk/provider`): `text-start {id}`, `text-delta {id, delta}`, `text-end {id}`, `finish {finishReason, usage}`, and `error {error}`. The `finishReason`/`usage` exact shape for V4 should be copied from `node_modules/@ai-sdk/provider/dist/index.d.ts` (`LanguageModelV4StreamPart` `finish` member) at implementation time [VERIFIED: codebase for part names; finish shape: check d.ts].
```ts
// src/lib/ai/mock-model.ts  (illustrative; confirm 'finish' shape in d.ts)
import { MockLanguageModelV4, simulateReadableStream } from "ai/test";
export function createE2EMockModel(prompt: string) {
  const fail = prompt.includes("__e2e_error__");
  return new MockLanguageModelV4({
    doStream: async () => ({
      stream: simulateReadableStream({
        initialDelayInMs: 50, chunkDelayInMs: 30,
        chunks: [
          { type: "text-start", id: "t" },
          ...chunk(FIXED_COMPONENT).map((delta) => ({ type: "text-delta", id: "t", delta })),
          ...(fail ? [{ type: "error", error: new Error("mock mid-stream failure") }]
                   : [{ type: "text-end", id: "t" }, { type: "finish", /* finishReason+usage per V4 d.ts */ }]),
        ],
      }),
    }),
  });
}
```
Notes: for the error scenario put the `error` part AFTER at least 2 text-deltas (the route peeks the first delta; an error before it becomes 502/429 instead of mid-stream). The prompt is available in `doStream(options)` as `options.prompt` (array of messages) - or simpler, build the model per request from `parsed.prompt` (preferred: `getModel(prompt)`).
`ai/test` imports only in the mock module; Next bundles it into the server route chunk - acceptable (it is a small module, no secrets). If bundle hygiene matters, use dynamic `await import("./mock-model")` inside the mock branch so production never even loads it [ASSUMED: Next tree-shakes dynamic import to a separate chunk].

### Pattern 2: Request-time env gating
```ts
// src/lib/ai/model.ts
export const MODEL_ID = "gemini-2.5-flash";
export function isE2EMock(): boolean {
  return process.env.UIFORGE_E2E_MOCK === "1" && process.env.VERCEL_ENV !== "production";
}
export async function getModel(prompt: string) {
  if (isE2EMock()) return (await import("./mock-model")).createE2EMockModel(prompt);
  return google(MODEL_ID);
}
```
- The `VERCEL_ENV !== "production"` belt-and-braces guard makes activation impossible on Vercel Production even if the var is mis-set [CITED: vercel.com/docs/environment-variables/system-environment-variables - `VERCEL_ENV` is production|preview|development]. Locally and in CI `VERCEL_ENV` is undefined, so the guard passes.
- Server `process.env.X` in a Node route handler is NOT inlined at build (only `NEXT_PUBLIC_*` is inlined into client bundles) and is read per request, so the e2e env var works with `next build && next start` and is also set at build time harmlessly [ASSUMED: standard Next behavior; confirm by the e2e passing - if the first run shows real Google calls, move the read inside the handler].
- Do NOT use `NEXT_PUBLIC_` for this var.
- Replace `export const model` usage; update `route.test.ts` mock (`vi.mock("@/lib/ai/model", () => ({ getModel: async () => ({}) , isE2EMock: () => false }))`).

### Pattern 4: Sliding-window rate limiter (pure + injectable clock)
```ts
// src/lib/rate-limit.ts
const hits = new Map<string, number[]>();           // module-level, per serverless instance
export function checkRateLimit(key: string, { max, windowMs }: {max:number;windowMs:number}, now = Date.now()) {
  const cutoff = now - windowMs;
  const arr = (hits.get(key) ?? []).filter((t) => t > cutoff);
  if (arr.length >= max) {
    hits.set(key, arr);
    return { ok: false as const, retryAfterSec: Math.max(1, Math.ceil((arr[0] + windowMs - now) / 1000)) };
  }
  arr.push(now); hits.set(key, arr);
  if (hits.size > 5000) for (const [k, v] of hits) if (v[v.length - 1] <= cutoff) hits.delete(k); // lazy cleanup
  return { ok: true as const };
}
export function clientIp(req: Request): string {
  return req.headers.get("x-forwarded-for")?.split(",")[0]?.trim()
      || req.headers.get("x-real-ip")?.trim() || "unknown";
}
export function __resetRateLimit() { hits.clear(); }  // tests only
```
- Env: `RATE_LIMIT_MAX` (default 5), `RATE_LIMIT_WINDOW_MS` (default 60000), parsed with fallback to defaults on NaN.
- Place in `route.ts` after body validation, before key check/`streamText`. Response: `new Response("rate_limited", { status: 429, headers: { "Retry-After": String(sec) } })` - identical body to existing `failureResponse` 429 so the client path (`friendlyGenerateError`: message `rate_limited` -> `RATE_LIMIT_MESSAGE`) is unchanged. Check how the client turns a 429 response into `Error("rate_limited")` (Phase 3) - no UI change expected [VERIFIED: generate-error.ts matches `error.message === "rate_limited"` and `\b429\b`].
- Tests: use `vi.useFakeTimers()` + `vi.setSystemTime`, or pass `now` explicitly (preferred: no fake timers needed). Reset the Map in `beforeEach`. Route test: send 6 requests with the same `x-forwarded-for` -> 6th is 429 with `Retry-After`; different IP unaffected; the existing route tests (which send no IP header -> "unknown" bucket, many requests) need `__resetRateLimit()` in `beforeEach` or they will start hitting the limit.
- Vercel: `x-forwarded-for` is set by the platform (client-supplied values are overwritten), first entry is the client IP [ASSUMED from Vercel docs memory; verify at https://vercel.com/docs/headers/request-headers]. Locally behind no proxy there is no header -> "unknown" shared bucket (fine for dev; e2e overrides limits).

### Pattern 5: Playwright config (prod build)
```ts

export default defineConfig({

Safer: add npm script `"e2e:server": "next build && next start -p 3100"` and use `command: "npm run e2e:server"`.

- Download: `const [dl] = await Promise.all([page.waitForEvent("download"), page.getByRole("button",{name:"Baixar"}).click()]); expect(dl.suggestedFilename()).toBe("FixtureCard.tsx")` (name derived from the mock component's `export default function X`). - Mobile: `test.use({ viewport: { width: 390, height: 844 } })` (< md breakpoint 768px, where the tablist is visible: `md:hidden`). Assert `getByRole("tab",{name:"Código"}).click()` -> `getByRole("tabpanel")` visibility / `aria-selected`.
- Locators available (verified in source): textbox `aria-label="Prompt"`, button "Gerar", status `aria-live` text "Gerando…"/"Pronto", `role="alert"` + button "Tentar de novo", tabs "Preview"/"Código", buttons "Copiar"/"Baixar", iframe `title="Live preview"`. Note two elements carry `aria-label="Live preview"` (section and iframe) - use `page.locator('iframe[title="Live preview"]')` or `page.frameLocator('iframe[title="Live preview"]')`. In desktop layout the "Resultado" tablist is `md:hidden` (hidden) so desktop tests do not see tabs.
- `PromptForm` Gerar disabled until prompt non-empty; Ctrl+Enter also submits.

### Pattern 6: Asserting inside the srcdoc sandboxed iframe
- `page.frameLocator('iframe[title="Live preview"]').getByText("...")` works for `srcdoc` iframes with `sandbox="allow-scripts"` (no same-origin) because Playwright drives frames over CDP, not through JS same-origin access [ASSUMED - MEDIUM; confirm in first run]. 
- **Network:** the iframe loads Tailwind (`@tailwindcss/browser@4.3.3`), React 18.3.1 UMD, ReactDOM and `@babel/standalone@7.28.5` from `cdn.jsdelivr.net`. If those fail to load, the iframe shows `uiforge-error` "Falha ao carregar o runtime do preview." GitHub-hosted runners have internet, so a real render assertion works in CI; it is a flakiness risk (CDN outage, offline dev machine). Recommendation: assert (a) iframe `toBeVisible()` + `srcdoc` attribute contains the component text (offline-safe, always), and (b) the rendered text via `frameLocator` with `timeout: 20_000` (network-dependent). Keep (b) in the happy-path test; do NOT add `page.route` CDN stubs (routing intercepts iframe subrequests but replicating Babel/React is not worth it). Document the CDN dependency as a trade-off in the README (A vendoring alternative is a v2 item).
- `preview-ready` postMessage arrives only after successful render; the host shows no explicit "ready" node, so assert on component DOM.

## Common Pitfalls

### Pitfall 1: Missing API key breaks e2e/CI
**What goes wrong:** route returns 500 "Missing GOOGLE_GENERATIVE_AI_API_KEY" in CI. **How to avoid:** bypass the check when `isE2EMock()`. **Warning signs:** happy-path test shows the friendly error.

### Pitfall 2: Rate limit starves e2e
**What goes wrong:** scenarios (happy, error, retry, copy/download, mobile) issue >5 POSTs/min from the same IP bucket ("unknown" or 127.0.0.1) -> 429. **How to avoid:** `RATE_LIMIT_MAX=1000` in `webServer.env`; dedicated test for limiter itself in Vitest. Optionally one e2e that sets a tiny limit is NOT recommended (needs separate server).

### Pitfall 3: Existing route tests start tripping the limiter
Shared module-level Map across tests in the same file: call `__resetRateLimit()` in `beforeEach`, and mock `@/lib/ai/model` with new exports.

### Pitfall 4: Mid-stream error placement
Error part before the first `text-delta` becomes HTTP 502 (not mid-stream). Emit >=2 deltas first; verify the UI shows `role="alert"` and that preview was not promoted (shell clears `previewCode` on failure).

### Pitfall 5: `Retry` should resend last prompt
In the error scenario the retry re-sends the SAME prompt (`__e2e_error__`) and fails again. To prove "retry re-sends the last prompt", assert a second POST (via `page.waitForRequest` on `/api/generate` and compare `postDataJSON().prompt`), not a success. Alternatively make the mock fail only on the first N calls for that prompt - more state, avoid.

### Pitfall 6: CDN dependence in the preview iframe
See Pattern 6. Use generous timeout; split offline-safe assertions from CDN ones.

### Pitfall 7: Vitest sweeping `e2e/`
Exclude `e2e/**` or Vitest errors "Playwright Test did not expect test() to be called here".

### Pitfall 8: Playwright browsers on Windows/OneDrive path
Project path contains non-ASCII/OneDrive (`Área de Trabalho`). `playwright install` stores browsers in `%USERPROFILE%\AppData\Local\ms-playwright` (not in repo) - fine. `playwright-report/` and `.next/` inside OneDrive can cause sync locks; `reuseExistingServer` + not running `next build` concurrently with `next dev` on the same `.next` (use `next start` from build; do not run `npm run dev` while e2e builds) [ASSUMED].

### Pitfall 9: Preview deploys without key
By D-11 Previews return 500. Verify client shows generic friendly alert; consider returning JSON/short code rather than English prose (optional hardening; not required).

### Pitfall 10: First Vercel deploy before env var
Set env var, then redeploy. Also ensure GitHub repo is public before Vercel import for Hobby (Hobby supports private personal repos too; irrelevant).

### Pitfall 11: Branch rename
`git branch -m master main` before `git push -u origin main`; `gh repo create <name> --public --source=. --remote=origin` (do not use `--push` until user confirms).
